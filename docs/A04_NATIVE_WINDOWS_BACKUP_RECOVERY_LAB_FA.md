# آزمایشگاه بازیابی نسخه قدیمی در ویندوز مجازی — A04

این آزمایش پس از ساخت نسخه کاندید **فقط داخل GitHub Actions ویندوز** اجرا می‌شود و از نصب‌کننده عمومی اصلی `v2.0.3` برای تهیه یک snapshot واقعی سازگار با schema=6 استفاده می‌کند.

## سناریوی عملی

1. نصب واقعی NSIS نسخه عمومی `2.0.3` در مسیر موقت، راه‌اندازی `app.exe` بومی با WebView2 و تعیین رمز مدیر آزمایشی.
2. ساخت کالای ساختگی و پیش‌فاکتور ساختگی در IndexedDB نسخه ۶؛ استخراج `StorageService.exportAll()` نسخه قدیمی، تأیید حذف credentialها و نگهداری snapshot فقط در پروفایل آزمایشی روی ماشین مجازی.
3. ارتقای واقعی همان مسیر نصب به نسخه کاندید (بدون ایجاد GitHub Release)، ورود با همان رمز، تأیید حفظ کالا/فاکتور و مهاجرت نسخه پایگاه داده به ۷.
4. حذف عمدی **فقط دو رکورد آزمایشی**، بازیابی آنها با `StorageService.importAll` از snapshot تولیدشده در نسخه قبلی، بررسی مبالغ و نام محصول.
5. ردکردن snapshot با شناسه برنامه غیرمعتبر بدون اثر جانبی.
6. ایجاد رویداد حسابرسی ساختگی و آزمایش تراکنش برگشت اتمی در صورت تلاش برای بازنویسی رویداد قطعی؛ رکورد کالای تزریق‌شده نباید باقی بماند.
7. بستن برنامه، اجرای مجدد `app.exe` با پروفایل سابق، بررسی ماندگاری اطلاعات و ردپای حسابرسی؛ سپس نصب تازه در پروفایل جداگانه و تست بومی DPAPI.
8. ثبت گزارش‌های JSON بدون داده مشتری، نام واقعی، رمز یا کلید خصوصی در artifact سی‌روزه.

## محدودیت اعتبار

- این آزمایش، بازیابی **snapshot کامل سازگار با نسخه ۶** را کنترل می‌کند، نه لزوماً فرمت رمزگذاری‌شده `.fbackup` شرکت یا فایل تاریخی یک مشتری واقعی.
- داده‌های حسابداری این آزمایش ساختگی و بسیار کوچک‌اند؛ تست دفتر کل، صحت مالی مستقل، چاپ RTL چندصفحه‌ای، قطع برق و فرایند بازیابی مشتری همچنان گیت‌های جداگانه‌اند.
- مقدار `v2.0.4` صرفاً نسخه موقت CI برای آزمایش ارتقا است؛ به‌معنی انتشار نسخه 2.0.4 نیست.
- موفقیت این آزمایش تنها بخشی از شواهد A04/A07 است؛ وضعیت `docs/PHASE_A_RELEASE_ACCEPTANCE.json` بدون تأیید مستقل تغییر نمی‌کند.
