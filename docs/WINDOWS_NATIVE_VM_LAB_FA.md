# آزمایشگاه ویندوز بومی Factor-easyPro

## هدف و محدوده
این آزمایشگاه روی **Windows VM موقت GitHub Actions** اجرا می‌شود و فایل نصب‌کننده واقعی
Tauri/NSIS را نصب و در WebView2 بومی اجرا می‌کند. از صفحه `vite preview` به جای
برنامه دسکتاپ استفاده نمی‌شود. هیچ رکورد واقعی مشتری، رمز مشتری یا تغییر در نسخه
عمومی وجود ندارد.

فایل‌ها:
- `.github/workflows/windows-vm-native-lab.yml` — راه‌اندازی Windows VM و ثبت شواهد
- `scripts/windows-vm-native-lab.ps1` — نصب NSIS، ارتقای درجا و حذف نسخه آزمایشی
- `scripts/windows-vm-set-candidate.cjs` — افزایش موقت شماره نسخه صرفاً در فضای CI
- `tests/windows-vm-installed-tauri-cdp.cjs` — اتصال به WebView2 و آزمون‌ها

## روش اجرا
در GitHub Actions، workflow **Phase A Windows VM Native Installer and Upgrade Lab**
را با `workflow_dispatch` اجرا کنید، یا PR تغییردهنده اسکریپت‌های فوق بسازید.
هیچ فرآیند برنامه‌نویسی یا ماشین شخصی نباید روشن بماند.
هر بار یک Windows runner تمیز تخصیص داده می‌شود.

## کنترل‌های خودکار
۱. اجرای همه تست‌های Node و ساخت فرانت‌اند (از طریق Quality Gates).
۲. ساخت NSIS بومی ویندوز از کد همان PR؛ شماره نسخه کاندید فقط داخل runner تغییر می‌کند.
۳. دریافت فایل رسمی 2.0.3 و تطبیق SHA256 با checksum منتشرشده.
۴. نصب بی‌صدا و اجرای واقعی Tauri، ایجاد رمز مدیر آزمایشی، نوشتن رکوردهای مصنوعی
کالا/فاکتور در IndexedDB نسخه ۶.
۵. نصب کاندید روی همان مسیر و همان WebView2 profile و تأیید داده و ورود حفظ‌شده،
مهاجرت ۶ به ۷ و عدم تولید غیرواقعی سابقه حسابرسی.
۶. نصب تازه کاندید با پروفایل مستقل، ساخت مدیر و بررسی Windows DPAPI.
۷. در نصب تازه، ایجاد شخص و کالا از طریق کنترلرهای واقعی، خروجی پشتیبان کامل
بدون فیلدهای رمز، بازپخش بدون تکرار رکورد، و بازکردن هر ۱۰ صفحه اصلی از Router واقعی.
۸. تلاش برای ثبت تصویر PNG محیط بومی و خروجی JSON برای هر سناریو؛
اگر تصویر به‌دلیل محدودیت CDP پشتیبانی نشود، صریحاً `UNVERIFIED` ثبت می‌شود.
۹. پاک‌سازی فایل‌های نصب‌شده و پروفایل‌های موقت با پایان عمر runner.

## مدرک قابل ارزیابی
هر اجرای CI، artifact با نام `phase-a-native-windows-vm-evidence` را نگه می‌دارد.
چهار فایل JSON (seed، upgrade، fresh و summary) به همراه تصویر احتمالی PNG
در آن هستند. موفقیت workflow باید بر اساس مقادیر `status=PASSED`،
نتایج مستقل و سبز بودن تمام Quality Gates تأیید شود، نه صرف وجود artifact.

نمونه اولین اجرای موفق نصب/ارتقا:
[Windows VM run 38920001588](https://github.com/davoodmehraban89/Factor-easyPro/actions/runs/38920001588).

## محدودیت‌های صریح
- این آزمون **نصب واقعی NSIS و استفاده واقعی WebView2** است، ولی کاربر واقعی و
پرینتر فیزیکی ندارد.
- بازپخش یک پشتیبان مصنوعی معادل بازیابی فایل واقعی مشتری یا قطع برق وسط Restore نیست.
- آزمون navigation همه صفحات، تأیید تک‌تک فرم‌ها و تمام عملیات پیچیده مالی نیست.
- چاپ RTL روی کاغذ، فونت‌های سیستم مشتری، نصب روی Windows با محدودیت سازمانی،
مهاجرت فایل‌های ناشناخته نسخه‌های قبل از 2.0.3، و سناریوهای خطای سخت‌افزار
هنوز پذیرش دستی یا آزمایشگاه تخصصی بیشتری می‌خواهند.
- نسخه رسمی 2.0.3 در فایل `src/main.js` خود برچسب رابط `1.1.1` را به‌صورت
ثابت داشت. آزمایشگاه این مغایرت تاریخی را گزارش می‌کند؛ نسخه کاندید جدید
باید برچسب درست منطبق با فایل manifest نشان بدهد.
