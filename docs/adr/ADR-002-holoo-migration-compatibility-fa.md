# ADR-002 — سازگاری هلو بدون وابستگی به دیتابیس داخلی آن

**وضعیت:** قرارداد معماری و ابزار پیش‌بررسی اولیه آماده؛ **مهاجرت بکاپ هلو هنوز اجرا نشده و تأیید نشده است**.  
**مالک اجرا:** مهندسی داده (A02). **بازبین:** حسابداری مستقل و امنیت داده.  
**وابستگی:** دریافت کپی مجاز بکاپ یا خروجی هلو + تعیین نسخه و فرمت واقعی.

## تصمیم
- ساختار داخلی فینورا (IndexedDB v7، کدینگ دوبل، گزارش مغایرت و Audit) مستقل و قابل ارتقا باقی می‌ماند. **هیچ جدول یا قالب ذخیره‌سازی هلو عیناً وارد هسته فینورا نمی‌شود.**
- برای هر نسخه/فرمت پشتیبانی‌شده هلو، آداپتور جدا ساخته می‌شود: «خواندن ورودی مجاز → تفسیر مستند جدول و ستون → تبدیل نوع/واحد پول و شناسه → مدل میانی ثابت → بررسی مغایرت → پیش‌نمایش → تأیید صریح مهاجرت». شکست در هر مرحله، عملیات را متوقف می‌کند.
- واردکردن کل فایل Backup یا اتصال مستقیم به دیتابیس هلو **به معنای پشتیبانی نیست**؛ رمزگذاری، فرمت اختصاصی، نیاز به ابزار رسمی یا مجوز، فقط پس از دیدن فایل واقعی ارزیابی می‌شود. برای خروجی رسمی Excel/CSV/JSON نیز نام و معنای ستون‌ها باید از همان نسخه مستند شود.

## نقشه داده مورد نیاز
| بخش تجاری | داده هلو پس از تفسیر مستند | ساختار مقصد فینورا |
|---|---|---|
| اشخاص | شناسه پایدار، نام، مانده بدهکار/بستانکار | contacts + حساب‌های دریافتنی/پرداختنی + افتتاحیه |
| کالا | شناسه کالا، واحد، گروه و بهای موجودی | products, warehouses, inventory_balances |
| فاکتور | شماره و تاریخ، نوع، شخص، اقلام، تخفیف/مالیات، پرداخت | invoices, invoice_items و ارجاع به اسناد مهاجرت |
| چک و بانک | جهت، مبلغ، سررسید، وضعیت، طرف حساب، حساب بانک | cheques, treasury و وضعیت مالی مرتبط |
| اسناد حسابداری | شماره/تاریخ سند، کدینگ بدهکار/بستانکار | account_chart, journal_entries, journal_lines |
| تاریخچه تغییرات | اسناد اصلاحی، شماره مرجع، وضعیت منبع | document_corrections و audit_events فقط برای عملیات فینورا |

این جدول **نگاشت نیازمندی** است؛ نام جدول/ستون یا فرمت واقعی بکاپ هلو را ادعا نمی‌کند.

## معیارهای تطبیق و پذیرش
۱. قبل از نوشتن، snapshot رمزگذاری‌شده با اجازه مالک نگه‌داری و SHA-256 آن ثبت می‌شود. اصل فایل تغییر نمی‌کند؛ تست مخرب فقط روی کپی ایزوله است.
۲. شرکت مقصد از ابتدا مشخص است؛ هر شناسه منبع به شناسه جدید شرکت مقصد با نگاشت صریح و پایدار تبدیل می‌شود. تکرار مهاجرت نباید سند یا مانده تکراری تولید کند.
۳. به‌جای ثبت مجدد همه فاکتورهای تاریخی از مسیر صدور زنده و ایجاد گردش دوباره انبار، **سیاست انتقال تاریخچه یا فقط مانده افتتاحیه** باید با حسابدار انتخاب شود. اختلاف‌ها، فاکتورهای نامعتبر و رکوردهای یتیم نباید بی‌صدا اصلاح شوند.
۴. تطبیق ریالی قبل/بعد، تراز بدهکار/بستانکار، جمع ریز مانده اشخاص، بهای انبار، چک‌ها، تسویه‌ها و دوره مالی ضروری است؛ واحد پول (تومان/ریال)، گردکردن، تاریخ شمسی و واحد کالا باید صریح تعیین شوند.
۵. در صورت ناسازگاری schema، نامعلوم بودن ستون، داده حساس، فقدان مرجع یا کمبود اطلاعات، **fail closed** و گزارش کد مشکل بدون نمایش نام اشخاص/شماره چک. خروجی نسخه آزمایشی حق نوشتن در دیتابیس واقعی را ندارد.
۶. تنها پس از گزارش تطبیق و تأیید مستقل می‌توان در رابط فینورا دکمه مهاجرتِ واقعی با تأیید صریح و rollback را طراحی کرد. نسخه هلو و حد و مرز اطلاعات قابل انتقال در بازاریابی شفاف اعلام شوند.

## آنچه هم‌اکنون پیاده‌سازی شد
ماژول `src/core/HolooMigrationPreflight.mjs` یک پیش‌بررسی **صرفاً حافظه‌ای و غیرمخرب** برای داده‌های جدولی از پیش استخراج‌شده و ستون‌های **صریحاً نگاشت‌شده** فراهم می‌کند. این ماژول شناسه‌های تکراری، ارجاع یتیم، مبلغ غیرصحیح ریالی و بیش‌پرداخت را پیدا می‌کند؛ گزارش فقط کد و شماره ردیف دارد و ورودی یا دیتابیس را تغییر نمی‌دهد. نتیجه موفق هم فقط `requires-source-and-accountant-review` است و **مجوز commit نیست**. آزمون‌ها کاملاً ساختگی‌اند و ادعای خواندن مستقیم `.bak` یا بکاپ اختصاصی هلو ندارند.

## پشتیبانی اولیه از خروجی CSV/TSV، با واحد پول صریح

ماژول `src/core/HolooDelimitedExportPreflight.mjs` اکنون می‌تواند **فقط متن خروجی جدولی استخراج‌شده** را با `delimiter` صریح (کاما، سمی‌کالن یا Tab) و `mappings` صریح ستون‌ها بررسی کند. BOM، نقل‌قول‌های دوتایی، متن چندخطی، ستون تکراری، سطر ناقص، حجم ورودی و ارجاع جدول والد کنترل می‌شود. واحد پول باید `rial` یا `toman` باشد؛ تبدیل تومان به ریال تنها با همین ورودی صریح و کنترل سرریز انجام می‌شود. هیچ فرمت یا واحد پولی از روی نام فایل یا محتوای خصوصی حدس زده نمی‌شود.

نمونه قرارداد **ساختگی** و نه ادعای نام ستون واقعی هلو:

```js
previewHolooDelimitedExport({
  sourceSystem: 'holoo', moneyUnit: 'rial',
  tables: { products: { text: 'id,name\nP1,Sample\n', delimiter: ',' } },
  mappings: { products: { sourceId: 'id', name: 'name' } }
})
// { canCommit: false, status: 'requires-source-and-accountant-review', ... }
```

تمام نتایج فقط شمارش رکورد، کد ایراد و شماره ردیف‌اند؛ **متن خام فایل، نام شخص، شماره حساب و شماره چک در خروجی قرار نمی‌گیرد**. هنوز تشخیص اصالت فایل هلو، خواندن `.bak`، تبدیل کامل فاکتورها و ثبت داده در دیتابیس مقصد پشتیبانی نمی‌شود. برای مانده افتتاحیه واقعی باید همه جدول‌های مربوط و تأیید حسابدار فراهم باشد.

## کنترل تطبیق جمع‌ها با گزارش منبع — مرحله بدون نوشتن

پیش از مهاجرت، اپراتور می‌تواند جمع‌های اعلامی در گزارش حسابداری **همان نسخه هلو** را در `declaredControlTotals` وارد کند؛ از جمله تعداد رکوردها، جمع مبالغ ریالی فاکتورها، وصول‌شده‌ها، مطالبات/بدهی اشخاص و چک‌ها. ماژول فقط با ارقام صحیح و محدودشده، تعداد ردیف‌های استخراج‌شده و جمع همان ستون نگاشت‌شده را مقایسه می‌کند؛ مبلغ‌ها با `moneyUnit` صریح به **ریال** تبدیل شده‌اند. اختلاف تعداد، مبلغ، ستون غایب، مجموعه داده غایب، مقدار نامعتبر و سرریز جمع، `blocked` می‌شوند. کد اختلاف‌ها **هیچ مبلغ یا نام شخصی نشان نمی‌دهد**.

این ارقام `declared` ادعای منبع هستند و **به‌خودی‌خود قابل اعتماد نیستند**؛ `independentlyVerified:false` و `canCommit:false` حتی در حالت تمام تطبیق‌ها باقی می‌مانند. این ابزار فقط مرحله اولیه گزارش مالی با داده مصنوعی/جدولی است؛ نه ابزار تبدیل بکاپ اختصاصی و نه پذیرش حسابدار. برای داده واقعی هنوز نیاز به فایل مجاز و کنترل مستقل داریم.

## سخت‌گیری در ورودی‌های استخراج جدولی — 2026-10-18

پیش‌بررسی CSV/TSV سطر خالی را بی‌صدا حذف نمی‌کند (`CSV_EMPTY_RECORD`)؛ نگاشت دو فیلد معنایی به یک ستون خام را رد می‌کند (`CSV_DUPLICATE_SOURCE_COLUMN_MAPPING`) و `declaredControlTotals: {}` را به‌عنوان کنترل انجام‌شده نمی‌پذیرد (`CONTROL_TOTALS_SCHEMA_INVALID`). این کنترل‌ها فقط بر داده مصنوعی/ازپیش‌استخراج‌شده اعمال می‌شوند و همچنان اعتبار بکاپ هلو، تطبیق مستقل حسابدار یا مجوز import را ثابت نمی‌کنند.

## مانع مرحله بعد
**نیاز به یک فایل واقعی متعلق به مالک** است (فایل اصلی بدون تغییر می‌ماند). ابتدا پسوند، امضای فایل، نسخه هلو و امکان خواندن امن/مجاز در محیط ایزوله بررسی می‌شود. سپس آداپتور همان فرمت بر اساس شواهد واقعی توسعه داده می‌شود. پیش از اتصال به CI عمومی، اطلاعات اشخاص، مالی، بانکی و رمزها حذف/ناشناس می‌شوند.

## گزاره بازاریابی پیشنهادی (مشروط)
«انتقال کنترل‌شده کالا، اشخاص و مانده‌های تأییدشده از نسخه‌های پشتیبانی‌شده هلو به فینورا، با گزارش مغایرت قبل از ثبت». تا زمان عبور تست‌ها، عبارت «انتقال کامل تمام اطلاعات همه نسخه‌های هلو با یک کلیک» نباید استفاده شود.
