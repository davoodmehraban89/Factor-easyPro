# ADR-003 — حاکمیت اجرایی Factor-easyPro با ساختار ۵+۱+۳

**وضعیت:** Proposed — پیشنهاد مالک؛ هنوز تصویب یا به‌طور مستقل تأیید نشده است
**تاریخ:** 2026-10-30
**Issue:** [#142](https://github.com/davoodmehraban89/Factor-easyPro/issues/142)
**وابستگی حفاظتی:** [#19](https://github.com/davoodmehraban89/Factor-easyPro/issues/19)

## زمینه و مرجع معتبر

این تصمیم برای کاهش ریسک خطاهای مالی، تکرار توسعه، خودتأییدی و انتشار زودهنگام پیشنهاد می‌شود. نقشه راه موجود و ترتیب فازهای A→B→C حفظ می‌شود. `PROJECT_STATUS.md` مرجع گزارش وضعیت است؛ `docs/PHASE_A_RELEASE_ACCEPTANCE.json` تنها مرجع ماشینی گیت‌های فاز A است. این ADR دفتر وضعیت موازی نمی‌سازد و مقادیر acceptance را تغییر نمی‌دهد. `STATUS.md` تاریخچه‌ای قدیمی دارد و بر داده جدیدتر و ماتریس ماشینی مقدم نیست.

در بررسی 2026-10-30 شاخه `main` بدون protection و Ruleset اجباری بود. وجود ۹ نقش در این سند **دلیل وجود ۹ عامل مستقل** نیست. اتصال GitHub توان خواندن/نوشتن مستندات، PR و مشاهده CI را فراهم می‌کند؛ استقلال حسابرس مالی یا ممیز امنیتی را ایجاد نمی‌کند. هماهنگی با Davood-AI-OS تا زمان وجود شواهد اتصال واقعی صرفاً هدف طراحی است.

## تصمیم پیشنهادی و مالکیت

**مالک محصول:** Davood، مرجع نهایی تصمیم‌های تجاری/حسابداری، هزینه جدید، داده واقعی، اختیارهای جدید و Release عمومی.

**PM — مدیر ارشد:** بازیابی وضعیت زنده GitHub؛ اولویت‌بندی یک وظیفه کوچک؛ تخصیص دقیق یک نقش پاسخگو؛ تعریف Base SHA، مسیر مجاز، وابستگی، آزمون، ریسک و rollback؛ جلوگیری از تعارض فایل‌ها؛ جمع‌آوری خروجی و شواهد. PM مجاز به تأیید مستقل کار خود نیست.

### پنج نقش اجرایی تخصصی

| شناسه | تخصص | مسئولیت‌های کلیدی |
| --- | --- | --- |
| A1 | Financial Accounting & Treasury | حسابداری دوبل، کدینگ و دوره مالی، سند قطعی/اصلاحی/برگشتی، خزانه/بانک/صندوق/چک، تسویه، تطبیق دفتر |
| A2 | Sales, Inventory & Business Processes | خرید/فروش/پیش‌فاکتور، مرجوعی، موجودی و انبارگردانی، بهای تمام‌شده و اثر عملیات بر دفتر، طراحی B/C مشروط به گیت ورود |
| A3 | Architecture & Data Integrity | Tauri/Vite/IndexedDB، تراکنش اتمی، تفکیک شرکت‌ها، Audit، idempotency، migration/rollback و backup/restore |
| A4 | Windows App, UX & Reporting | RTL، گردش با صفحه‌کلید، گزارش/چاپ PDF/CSV/Excel، WebView2، NSIS، نصب/ارتقا/آفلاین و آزمون Windows |
| A5 | QA, Security & DevSecOps | تست واحد/یکپارچه/منفی/رگرسیون، لایسنس و مجوز، امنیت وابستگی‌ها، CI/Artifacts، تست عملکرد و خطا |

اینها **نقش** هستند؛ فقط هنگامی «اجرا توسط ایجنت مستقل» گزارش شود که ابزار/هویت و خروجی مستقل همان اجرا مستند باشد. اگر تنها یک مدل نقش‌ها را تحلیل می‌کند، گزارش با عنوان «تحلیل داخلی» نوشته شود.

### سه کنترل مستقل، بعد از اجرای واحد کار

- **C1 — Technical, Architecture & Security:** Diff کامل، صحت معماری و داده، دسترسی/مجوز، ریسک امنیت، migration و rollback، سازگاری و نتیجه GitHub Actions روی SHA دقیق. خروجی: `PASS | FAIL | BLOCKED`.
- **C2 — Financial & Business Integrity:** توازن سند دوبل، مانده اشخاص/خزانه، چک/مرجوعی/بهای انبار، ریال صحیح، دوره بسته، تفکیک شرکت، عملیات اتمی و مقایسه محاسبه مستقل با داده آزمون مشخص. حتی برای PR اسنادی، «بدون تغییر منطق مالی» باید مستند و راستی‌آزمایی شود. خروجی: `PASS | FAIL | BLOCKED`.
- **C3 — Independent Release & Acceptance Governance:** پوشش Issue/معیارها، هویت مستقل C1 و C2، PR و Base/Head SHA، CI/Windows native، Artifact/hash، وضعیت گیت، محدودیت‌های واقعی، rollback و اختیار ادغام/انتشار. خروجی: `ACCEPT | REVISE | REJECT | BLOCKED`.

**تعارض منافع ممنوع:** نویسنده تغییر یا همان مدیر/عامل، حتی اگر سه بار با پرامپت متفاوت بررسی کند، «سه کنترل مستقل» به وجود نمی‌آورد. سه بازبینی متوالی داخلی مفید است ولی جایگزین تأیید مستقل نیست. فقدان فرد/عامل مستقل = `BLOCKED`، نه `PASS`. برای پذیرش نهایی مالیِ مستلزم قضاوت حرفه‌ای، حسابدار مستقل واجد صلاحیت باید نتیجه را امضا کند.

## چرخه اجباری هر واحد کار

1. **Recover:** وضعیت زنده `main`، Release، PRهای باز، Issues، Workflowها و گیت‌های A01..A08 و دو گیت بیرونی بررسی شود؛ شواهد قدیمی فقط سابقه‌اند.
2. **Define:** یک Issue غیرتکراری با هدف، صاحب نقش، ورودی/خروجی، Base SHA، فایل‌های مجاز/ممنوع، وابستگی، معیار پذیرش، سناریوهای منفی، ریسک مالی/امنیتی و rollback.
3. **Implement:** شاخه جدا، تغییر کوچک؛ خودداری از PR موازی در فایل مشترک؛ عدم دستکاری Production یا داده مشتری.
4. **Test:** `npm ci`, `npm test`, `npm run build`, ممیزی وابستگی‌ها و `git diff --check` به تناسب وظیفه؛ Workflowهای لازم از جمله `pr-quality-gates.yml` و `windows-vm-native-lab.yml`. هر مورد اجرا نشده `NOT_RUN` است، نه `PASS`.
5. **PR:** شرح Diff، Issue، Base و Head SHA، شواهد تست/CI، ریسک، داده واقعی، Limitations و rollback.
6. **Audit:** C1 و C2 و C3 با هویت و شاهد قابل‌راستی‌آزمایی؛ رفع اشکال و تکرار بررسی روی SHA جدید.
7. **Merge:** فقط با اختیار معتبر، کنترل مستقل، CI لازم و policy مخزن. هنگام نبود review مستقل، پذیرش/ادغام مسدود می‌ماند؛ عدم حفاظت فنی `main` مجوز خودادغامی نیست.
8. **Post-merge:** بررسی SHA و CI شاخه اصلی و به‌روزرسانی `PROJECT_STATUS.md`، Issue و ماتریس پذیرش **فقط پس از شواهد معتبر**؛ انتخاب دقیق یک اقدام بعدی.

**وضعیت‌های نهایی مجاز:** `ACCEPTED | REVISION_REQUIRED | REJECTED | BLOCKED | UNVERIFIED`. صرف ساخته‌شدن EXE، سبزشدن CI، رشد شمار تست‌ها یا شبیه‌سازی review، قبول گیت نیست.

## جداسازی شواهد و محدودیت ایمنی

- آزمون Node معادل WebView2 نصب‌شده نیست؛ نصب در Windows VM جای چاپگر فیزیکی یا سخت‌افزار نماینده را نمی‌گیرد.
- بکاپ مصنوعی و کشته‌شدن process اثبات بازیابی مشتری واقعی یا قطع برق فیزیکی نیست.
- هیچ سند قطعی بازنویسی/حذف نمی‌شود؛ عملیات مالی/انبار/خزانه باید در مرز تراکنشی اتمی، قابل‌ردیابی و company-scoped باشد.
- اطلاعات مشتری، رمز، کلید خصوصی، توکن و بکاپ واقعی وارد GitHub عمومی، CI، لاگ یا گفت‌وگو نمی‌شوند.
- مهاجرت هلو فقط preflight خواندنی روی داده مصنوعی/مجاز و محیط ایزوله است تا فرمت واقعی و تطبیق حسابدار مستقل تأیید شود.
- تغییر لایسنس Production، هزینه، داده واقعی، اقدامات مخرب یا انتشار رسمی نیازمند اختیار صریح مالک است.
- A03/A04 اگر در ماتریس accepted ثبت شده‌اند، محدوده شواهد همان پذیرش معتبر است؛ این امر به‌معنای تأیید کل فاز A نیست.

## قرارداد گزارش و معیار پذیرش این ADR

هر واحد کار گزارش می‌دهد: شناسه/فاز، هدف، پیش‌وضعیت، PM، نقش پاسخگو/همکاران، Base/Head SHA، Branch/PR، Diff، تست‌های اجراشده و اجرا‌نشده، CI، Windows Native، C1/C2/C3 با هویت بازبین، داده واقعی، ریسک، rollback، وضعیت و **یک** اقدام بعدی.

این ADR زمانی از **Proposed** به **Accepted** تغییر می‌کند که PR مستنداتی توسط شخص/عامل واقعاً مستقل بازبینی، کنترل‌های مرتبط ثبت و با اختیار معتبر ادغام شده باشد. صرف ایجاد PR و عبور CI، خودبه‌خود پذیرش سیاست نیست. ADR با تصمیم مستند جدید و مسیر PR قابل اصلاح است؛ تاریخچه تصمیم پاک نمی‌شود.

## گزینه‌های ردشده

- استفاده از ۹ عنوان با یک مدل و ادعای ۹ ایجنت واقعی: استقلال کاذب و خطر Self-approval.
- بازکردن گیت انتشار فقط با CI سبز: آزمون‌های بیرونی و مالی پوشش داده نمی‌شوند.
- ایجاد فایل موازی `PHASE_STATUS_NEW.md`: واگرایی وضعیت و احتمال پذیرش اشتباه.
- تبدیل اتصال Davood-AI-OS به پیش‌شرط بدون شواهد اتصال: وابستگی ساختگی.
