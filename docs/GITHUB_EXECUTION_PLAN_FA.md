# برنامه اجرایی GitHub-only برای Factor-easyPro — رقابت ماژولار با هلو

**ثبت:** ۱۴۰۵/۰۷/۲۱ (۲۰۲۶-۱۰-۱۳) | **مبنای قابل تأیید:** v2.0.3 | **وضعیت:** برنامه مصوب؛ قابلیت‌های فازهای آینده هنوز پیاده‌سازی نشده‌اند.

## ۱. مرجع تصمیم و محدوده
- هدف نهایی: پلتفرم فارسی **حسابداری + فروشگاهی + بازرگانی + تولید + پخش** با هسته مشترک و افزونه‌های مستقل؛ نه کپی کد/طراحی/کدینگ مالکیتی هلو.
- نقشه جامع امکانات و ترتیب: [ROADMAP_HOLOO_COMPETITOR_FA.md](ROADMAP_HOLOO_COMPETITOR_FA.md).
- هسته موجود: Tauri 2 / Vite / IndexedDB، نسخه منتشرشده 2.0.3، مجموعه ۷۳ تست خودکار در آخرین CI انتشار. این رقم اثبات تمام سناریوهای واقعی یا امنیت نیست.
- توسعه و تست بدون Remote Desktop از GitHub Branch → Pull Request → GitHub Actions → Release. **هیچ CI به داده واقعی کاربر دسترسی ندارد**.
- معماری آفلاین تک‌دستگاهی تا زمانی‌که C08 و ADR معماری شبکه واقعاً پیاده‌سازی/آزموده شوند، حفظ می‌شود.

## ۳. ترتیب اولویت دقیق (اولویت پیشنهادی تجاری و ریسک)

### A — قبل از هر گسترش
۱. **A01 + A03:** طراحی ADR و اجرای اصلاح/ابطال سند با اثر برگشتی اتمی؛ رویداد حسابرسی شامل actor/company/document/correlation؛ تست repeat و rollback.
۲. **A04 + A02:** نسخه پشتیبان سازگار، بازیابی تمرینی، افتتاحیه و مهاجرت شرکت دارای تاریخچه با dry-run و گزارش اختلاف؛ بدون بازنویسی خودکار داده زنده.
۳. **A05 + A06:** کنترل بستن دوره و خزانه، مجوزهای واقعی در لایه سرویس، مدل لایسنس امضاشده و محرمانگی.
۴. **A07 + A08:** آزمون نصب و ارتقای ویندوز، چاپ PDF چندصفحه‌ای و RTL، تست فشار و خرابی و پایش خطا.

### B — رقابت فروشگاهی
۱. **B01 → B02 → B03:** POS کیبورد/بارکد، چندپرداخت اتمی، بستن شیفت، چندقیمت و تخفیف با کنترل اختیار.
۲. **B04 → B05:** سفارش/تأمین، دریافت/تحویل جزئی، رزرو موجودی، بارکد/چاپ لیبل و دوواحدی.
۳. **B06 → B07 → B09:** اعتبار و سررسید، سود بهای تمام‌شده و داشبورد، ورود/خروج استاندارد و راهنمای کاربر.
۴. **B08:** اتصال ادوات فقط پس از ثبت مدل دستگاه، درایور و نتیجه پذیرش واقعی.

### C — توان رقابت در حوزه‌های متعدد
۱. **C01 + C03:** تولید/BOM و بهای صنعتی، با آزمون مصرف مواد و ارزش محصول.
۲. **C02 + C06:** پخش/ویزیتور/پورسانت و پروژه/قرارداد.
۳. **C04 + C05:** اموال/استهلاک و حقوق/دستمزد پس از بررسی تخصصی قانون.
۴. **C07:** صورتحساب الکترونیکی تنها پس از مستندسازی الزامات رسمی، محیط آزمون و پاسخ سامانه.
۵. **C08 + C09:** معماری سرور تراکنشی، مهاجرت اطلاعات آفلاین، API/همگام‌سازی با بودجه/تصمیم جداگانه.
۶. **C10:** کیت‌های صنفی (پوشاک، خواربار/تاریخ انقضا، خدمات، رستوران و...) تنها براساس تقاضای اثبات‌شده.

## ۴. قرارداد هر Issue
هر Issue اجرایی باید شامل **یک مالک مسئول** (نقش، نه انتساب جعلی کاربر GitHub)، مسئله و جریان کاربر، ورودی/خروجی، قرارداد داده، وابستگی، اثر مالی/امنیتی، migration، test matrix، شرایط خطا، معیار پذیرش و محدودیت‌های اعلام‌شده باشد.
- شناسه، اولویت، فاز در عنوان: `[A02][P0]`، `[B01][P1]`، `[C01][P2]`.
- ۳ Epic ثبت‌شده: [A](https://github.com/davoodmehraban89/Factor-easyPro/issues/2)، [B](https://github.com/davoodmehraban89/Factor-easyPro/issues/3)، [C](https://github.com/davoodmehraban89/Factor-easyPro/issues/4).
- نقطه شروع قرارداد اسناد: [A01+A03](https://github.com/davoodmehraban89/Factor-easyPro/issues/5).
- Issue مستقل زمانی بسته می‌شود که PR ادغام‌شده، آزمون/گزارش قابل ارجاع و نتیجه پذیرش داشته باشد. داشتن UI تنها کافی نیست.

## ۵. مراحل PR / CI / Release
۱. از `main` شاخه `feature/<issue>-slug` یا `fix/<issue>-slug` ایجاد شود؛ هر PR یک دامنه و مالک.
۲. قالب PR تکمیل شود؛ ADR برای تغییرات حسابداری/Schema/مجوز/شبکه در `docs/adr/` لازم است.
۳. `pr-quality-gates.yml`: نصب تمیز `npm ci`، تست Node، Vite build، Windows x64 Tauri build و خروجی artifact **بدون انتشار عمومی**. تست سخت‌افزار/چاپ واقعی تا زمانی‌که وجود ندارد، «ناانجام» اعلام شود.
۴. تغییرات migration باید تست نسخه قبلی → جدید، backup → restore، fail/rollback و company isolation را داشته باشند.
۵. ادغام فقط بعد از بازبینی انسانی و سبزبودن checkها. اجرای موفق CI برابر با تایید تجاری/حسابداری مستقل نیست.
۶. Release جداگانه پس از تصمیم انتشار: tag SemVer، checksum SHA-256، یادداشت انتشار فارسی، EXE و بررسی لینک. Workflow تست PR حق انتشار یا دسترسی write ندارد.
۷. برای هر Release، شمار تست‌ها و نتایج ارتقا/رابط/چاپ/امنیت باید به همان نسخه نسبت داده شوند؛ از کپی ادعای تست نسخه قبلی خودداری شود.
۸. گزارش اشکال مشتری بدون dump خصوصی؛ با داده ساختگیِ قابل بازتولید و بدون token/password.

## ۶. تعریف «کامل» برای هر ماژول
- مسیر واقعی و منطق دامنه قابل اجرا، نه صفحات نمایشی.
- عملیات مالی مرتبط با ledger و stock **اتمیک** و قابل ردیابی؛ ثبت تکراری رد شود.
- دسترسی شرکت و نقش در سرویس بررسی شود؛ اطلاعات حساس audit/log mask شود.
- مهاجرت IndexedDB/restore نسخه‌دار و آزمایش‌شده باشد.
- Unit + integration + UI smoke + Windows build برای تغییرات مرتبط؛ خطای برگشتی بدون ثبت ناقص.
- RTL، دسترس‌پذیری/keyboard و چاپ در موارد مرتبط بررسی شود.
- محدودیت‌های شناخته‌شده، rollback و یادداشت‌های نسخه مستند باشد.

## ۷. خطرهای مانع‌ساز و تصمیم‌های آتی
- **P0:** مغایرت مالی یا خرابی داده واقعی → انتشار متوقف، بدون تلاش برای «اصلاح خودکار» بی‌مجوز.
- **P0:** تغییر ساختار حسابداری/IndexedDB بدون rehearsal migration و restore → PR رد شود.
- **P0:** مجوز و رمز: تغییرات فقط بعد از بررسی threat model، مفاهیم فعال‌سازی آفلاین و سیاست پشتیبانی.
- **P1:** تست ادوات (بارکدخوان/چاپگر/کارتخوان) بدون سخت‌افزار واقعی ممکن نیست؛ ادعای سازگاری نکنیم.

- **P2:** چندکاربره واقعی بر پایه IndexedDB تک‌کلاینتِ فعلی تحقق نمی‌یابد؛ قبل از شروع C08 طرح معماری/هزینه تایید شود.
