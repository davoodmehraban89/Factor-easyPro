# Factor-easyPro — نقشه راه جامع رقابت با هلو APEX

**نسخه سند:** 1.0 — 2026-10-13  
**مبنای کد:** Factor-easyPro 2.0.3 / `main`  
**وضعیت:** نقشه راه مصوب محصول؛ اقلام فازهای آینده تعهد انتشار یا قابلیت موجود محسوب نمی‌شوند.  
**هدف:** پلتفرم ماژولار فارسی حسابداری، بازرگانی، خرده‌فروشی، تولید و پخش برای کسب‌وکارهای ایران.

## ۱. مبنای وضعیت فعلی و تحلیل رقبا

کد کنونی مبتنی بر Tauri 2 + Vite + IndexedDB است. در مخزن ماژول‌های صدور فاکتور، اشخاص، کالا/انبار، خزانه/چک، حسابداری دوبل، کنترل مغایرت، گزارش‌گیری و نسخه پشتیبان وجود دارند. «وجود کد» به‌معنای کامل‌بودن تمامی سناریوهای کسب‌وکار نیست. نمونه موارد باز: اصلاح قطعی اسناد تجاری، مهاجرت شرکت‌های دارای گردش قدیمی، مجوز تجاری، آزمون نصب واقعی و چاپ فیزیکی. معماری فعلی آفلاین تک‌دستگاهی است؛ شبکه چندکاربره واقعی اثبات نشده است.

### الگوی هلو APEX (منابع بیرونی، نه قابلیت‌های پیاده‌شده ما)
- نسخه‌های فروشگاهی و صنفی: چند قیمت کالا، سفارش، چند انبار، صندوق، بارکد، چاپ لیبل، گزارش سود کالا/فاکتور، تجهیزات POS.
- نسخه‌های تولیدی و شرکتی: حسابداری، خزانه، بازرگانی، انبار، فرمول/تولید، حقوق و دستمزد، اموال.
- نسخه پخش: ویزیتور، سفارش‌گیری، پورسانت، تخفیف پلکانی، سفارش‌گیری سیار و توزیع.

## ۴. ترتیب اجرای نسخه‌ها (شماره‌ها پیشنهادی‌اند)

1. **2.0.4 — A01/A03:** چرخه اصلاح سند + دفتر ردپای عملیات؛ ابتدا طراحی شِمای تغییرناپذیر.
2. **2.0.5 — A02/A04:** مانده افتتاحیه، ابزار مهاجرت dry-run و بازیابی تمرینی.
3. **2.0.6 تا 2.2.x — A05..A08:** بستن دوره، دسترسی/لایسنس، سنجش عملکرد، چاپ/نصب و تثبیت.
4. **2.3 تا 2.5 — B01..B04:** POS، صندوق، چندروش پرداخت، قیمت و سفارش.
5. **2.6 تا 2.9 — B05..B09:** انبار پیشرفته، وصول، گزارش، ادوات و UX.
6. **3.x — C01..C07:** تولید، پخش، بهای صنعتی، اموال، حقوق، پروژه و مالیاتِ مشروط.
7. **3.x+ — C08..C10:** معماری شبکه/چندشعبه، API و کیت‌های صنفی؛ پس از تصمیم محصول و برآورد مستقل.

## ۵. مدل محصولات و بسته‌های آینده (نه قیمت‌گذاری مصوب)

## ۶. استاندارد اجرای GitHub-only

- **Single source of truth:** `main`، این سند، Issues و Pull Requests. دسترسی Remote Desktop دیگر شرط توسعه نیست.
- **Issue:** هر کار یک مالک اصلی، هدف، ورودی، وابستگی، قرارداد داده، خطر، معیار پذیرش و چک‌لیست آزمون.
- **Branch:** `feature/<issue>-short-name`، `fix/<issue>-short-name`، `release/vX.Y.Z`؛ تغییر مستقیم حساس در `main` ممنوع.
- **PR gates:** تست واحد/یکپارچه، lint/static check، build Vite، dependency/secret scan، گزارش migration، و برای تغییرات UI آزمون Windows WebView2/CDP در Runner.
- **داده آزمون:** فقط synthetic، بدون dump مشتری یا رمز در کد، Issue و لاگ عمومی.
- **نسخه‌گذاری:** semver؛ نسخه‌های ناسازگار با migration و rollback مصوب، release notes فارسی، نصب‌کننده Windows x64 و SHA-256.
- **Release:** GitHub Actions روی tag/commit تأییدشده؛ draft → بارگذاری asset → صحت فایل → انتشار. شکست هر gate = انتشار متوقف.
- **آزمون پس از build:** First-run، login، خرید/فروش/تسویه/برگشت، چاپ PDF (header/footer)، گزارش/بازیابی و uninstall/upgrade در ماشین موقت.
- **شواهد پذیرش:** لینک PR، اجرای CI، ماتریس test case، هش Release و مشکلات باقی‌مانده. تست دستی روی چاپگر یا دستگاه واقعی را انجام‌شده فرض نکنیم.
- **سیاست محافظت داده:** بدون پاک‌کردن دیتای واقعی؛ snapshot قبل از schema migration، تمرین بازگشت و کنترل مانده‌های حسابداری.
- **مدیریت اسناد:** ADR در `docs/adr/` برای معماری چندکاربره، حسابداری و مجوز؛ نگهداری changelog و راهنمای استقرار.

### حداقل ساختار GitHub
- سه Issue اصلی (Epic) برای A/B/C، با Sub-issues برای ماژول‌های جدول.
- برچسب‌ها: `priority:P0/P1/P2/P3`، `area:accounting/retail/inventory/enterprise`، `type:feature/bug/security/qa`، `status:blocked`.
- در صورت امکان، سه milestone با نام‌های `Phase A — Reliable Core`، `Phase B — Retail Pro`، `Phase C — Industry & Scale`.
- GitHub Actions برای PR و Release جدا باشند؛ ساخت منتشرشونده صرفاً بعد از تایید PR و نسخه.

## ۷. معیارهای غیرعملکردی هدف (اعداد، آزمون‌نشده)

- هیچ فاکتور قطعی نتواند سند نامتوازن یا گردش ناقص انبار تولید کند.
- خطای یک عملیات مالی، تمام تغییرات آن عملیات را rollback کند.
- بررسی عملکرد با **داده ساختگی ۱۰٬۰۰۰ کالا و ۵۰٬۰۰۰ فاکتور** برای نسخه Retail Pro؛ آستانه زمان پاسخ فقط پس از baseline واقعی تعیین شود.
- Restore نسخه‌دار باید در برابر نمونه سالم و نمونه خراب، نتیجه قطعی و قابل تشخیص بدهد.
- حداقل تست GUI روی Windows x64 و دو اندازه چاپ کاغذ؛ ادعای پشتیبانی سخت‌افزار نیازمند آزمایش واقعی است.
- سخت‌گیری مجوز صرفاً در UI کافی نیست: کنترل‌ها در سرویس و API اعمال شوند.
